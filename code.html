Why this is here

Turning millions of documents into a variable used to be data collection. It is now a modeling decision, and it changes what a paper finds.

A keyword screen is not a measurement. What it misses never enters the sample, and nothing tells you what was lost. A commercial API reads the documents far better, but at corpus scale it is expensive, it cannot touch licensed data, and it is revised mid-project — score the same documents twice, months apart, and the two runs no longer agree.

So I distill instead. Label tens of thousands of documents carefully, fine-tune an open-weight model on those labels, then run it locally over everything. What comes out is fixed: it does not change under you, it costs nothing per document once trained, and the data never leaves the machine.

I publish the pipelines so the measurement behind a paper can be checked and rebuilt, not taken on trust.

llm-finetuning — QLoRA for structured document classification

The full working pipeline behind the executive-contract measurement in my SEC-filings project: fine-tune Qwen3-14B to read a document and emit a structured JSON record, then run it over a corpus of millions on consumer GPUs. Training, LoRA merging, AWQ quantization, resumable multi-GPU corpus inference, and evaluation that scores every runtime on byte-identical held-out documents.

Code only — no data, labels, corpus, or model weights. The README documents the whole procedure end to end, including which base model to pull from Hugging Face, the schema your own labeled data needs to be in, and the failure modes that cost me the most time.

Hardware you need
  • 12–16 GB
    Serve a 14B model at Q4_K_M or Q6_K. Fine-tune at the 8B scale.
  • 24 GB
    Fine-tune 14B on short documents. Serve 14B up to Q8_0, or 32B at Q4_K_M.
  • 32 GB and up
    Fine-tune 14B on long documents, or 32B at batch 1.

Model weights in VRAM

Qwen3-32B66 GB35 GB27 GB20 GB

Weights only — add 1–3 GB for the KV cache, more with large batches or long context. Below Q4 the savings are small and the accuracy cost is not.

Fine-tuning adds optimizer state and activations on top of the 4-bit weights: a QLoRA run on 14B peaks near 20 GB at 768-token sequences, and near 24 GB at 2,300 tokens with the batch halved; 32B peaks near 26 GB at batch 1. Sequence length moves this more than model size does, so halve the batch before reaching for a bigger card.

More than one card scales inference, not training: the inference scripts run one process per GPU over disjoint slices of the corpus rather than sharding a single model, so a second card roughly halves wall-clock time and needs no extra configuration.

The pipeline in four steps
  1. 01
    Label
    Stratified sample labeled under the exact prompt the model will be served with.
  2. 02
    Fine-tune
    QLoRA on a 4-bit base; the held-out split is frozen before training starts.
  3. 03
    Serve
    Merge the adapter, quantize to W4A16, run on vLLM with prefix caching.
  4. 04
    Evaluate
    Every runtime scored on identical documents, so quantization cost is visible.
